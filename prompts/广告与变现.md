# 广告与变现

覆盖 AdSense 接入、广告位对性能的影响、广告密度与内容质量信号、以及 `ads.txt` 排障。

## 零、AdSense 通过不等于网站质量全部通过

AdSense `Ready` 证明网站已完成所有权验证并通过该阶段的政策审核，可以开始展示广告；它不是 SEO、安全、性能、隐私、可访问性或工程门禁的全面认证。

接入或调整广告前后必须同时执行：

- `QUALITY_STANDARD.md` 的 P0 发布门禁和 AdSense 专项；
- `RULES.md` 的 `AD-*`、`PF-*`、`TR-10`、`OP-09~12`；
- `LAUNCH_CHECKLIST.md` 的生产证据链。

登录、账号、私有分享、错误、站内搜索和低质量页面默认不加载广告。广告资格与 Analytics 资格必须分开定义；动态路由应按 route family 显式声明，不能依赖精确路径偶然匹配。

> v1.0 的这份文件只讲了 `ads.txt` 放在哪个目录。那是一条排障笔记，
> 但真正决定变现站成败的是下面第一节和第二节——广告位是 CLS 失败的头号来源，
> 而广告密度直接影响 Google 对页面质量的判断。

## 一、广告位与 Core Web Vitals（最高优先级）

**广告是 CLS 失败的头号来源。** 广告异步加载，加载前高度为 0，加载后撑开，
把下方内容整体推走——这正是 CLS 的定义。

适用规则：`PF-01`（CLS ≤ 0.1）、`PF-04`（预留固定高度容器）

### 必须做

```css
/* 每个广告位都要有预留高度，按最常见的广告尺寸设定 */
.ad-slot {
  min-height: 280px;      /* 对应 336x280 / 300x250 */
  display: block;
  contain: layout;         /* 隔离布局影响 */
}

@media (max-width: 767px) {
  .ad-slot { min-height: 250px; }   /* 移动端常见 300x250 */
}
```

要点：

- **每个广告位都要预留高度**，按该位置最常出现的广告尺寸设定
- 响应式广告要按断点分别设定 `min-height`
- 广告未填充时保留占位高度，不要塌陷（塌陷同样产生 CLS）
- 首屏尽量不放广告——首屏广告同时伤害 LCP 和 CLS
- 广告脚本用 `async`，不要阻塞渲染
- 第三方脚本越多 INP 越差，控制数量

### 验证

改动广告位后必须重新实测（`PF-01`）：

```text
移动端 LCP ≤ 2.5s   实测：
移动端 INP ≤ 200ms  实测：
移动端 CLS ≤ 0.1    实测：
```

**CLS 要在真实广告填充的情况下测**，本地无广告时测出来的 CLS 没有意义。

## 二、广告密度与内容质量信号

Google 对「广告干扰主内容」有明确的负面判断。相关信号包括页面体验、
Better Ads Standards、以及 helpful content 相关的质量评估。

### 约束

- 首屏广告不得占据主要视觉区域，正文必须在首屏可见
- 不使用弹窗插页广告遮挡主内容（移动端尤其敏感）
- 广告不得与正文视觉上难以区分（伪装成内容的广告是明确违规）
- 段落间广告要有足够间隔，不要每两段插一个
- 不使用自动播放带声音的广告

### 判断标准

一个简单的自检：**去掉所有广告后，页面还剩下多少有价值的内容？**
如果去掉广告后页面显得空洞，那么这个页面本身就不满足 `CT-05`（本页独有内容），
广告只是掩盖了内容问题——参照 `CT-07`。

### `data-nosnippet`

不希望被搜索摘要或 AI 引用抓取的区块（如推广模块、免责声明），可以标注：

```html
<div data-nosnippet>此区块不会出现在搜索摘要中</div>
```

**不要对正文使用。** 它会同时影响普通搜索摘要和 AI 引用，
对以搜索流量为主的页面通常得不偿失（详见 `RULES.md` 的 `AI` 章节）。

## 三、AdSense 过审的实际门槛

被拒最常见的原因不是技术问题，而是内容不足。过审前确认：

| 项 | 要求 |
|---|---|
| 内容量 | 有实质内容的页面数量足够，不是几个占位页 |
| 内容原创性 | 不是采集、翻译搬运或纯 AI 泛文（`CT-03`、`CT-06`） |
| 信任页面 | About、Contact、Privacy Policy 齐全（`TR-01`、`TR-02`） |
| 导航 | 结构清晰，无死链（`LINK-08`） |
| 域名 | 使用提交审核的正式域名，已正常收录 |
| 流量 | 有一定真实访问（非硬性，但有帮助） |

**先让站点满足 `RULES.md` 的必须级规则，再去申请。** 反过来做通常是浪费时间。

### 过审后仍需持续验证

- 保存 AdSense `Ready` 的后台日期和证据，但不要把它写成“全站质量通过”。
- 根域 `ads.txt` 的 publisher ID 必须与后台一致，HTTP/HTTPS 与 www/非 www 均可到达规范文件。
- 广告上线后用真实广告填充重新测 LCP、INP、CLS。
- 首页、Privacy Policy 和产品说明必须与真实的数据存储、同步、Cookie 和广告行为一致。
- 面向 EEA、英国或瑞士投放个性化广告时，使用 Google 认证且集成 IAB TCF 的 CMP，并在目标地区验证接受、拒绝和撤回流程。
- CMP 认证只证明满足 Google 的接入要求之一，不代表完整法律合规。

## 四、ads.txt 排障

> 以下为 Codex / Claude Code 可直接使用的提示词。

```text
请检查当前网站的 Google AdSense 广告代码、ads.txt 和网站所有权验证配置，
确保能通过 AdSense 审核，并避免「Ads.txt 状态未找到」或「未授权」问题。

## 1. ads.txt 位置

Next.js 项目必须放在 public 目录：

    public/ads.txt

要求：
- 文件名全小写 ads.txt，不能是 Ads.txt
- 不要放在 app、pages、src 或其它目录
- 构建后必须能访问 https://你的域名/ads.txt

请检查项目中是否存在错误路径或错误大小写的 ads.txt，并给出修复方案。

## 2. ads.txt 内容

格式类似：

    google.com, pub-xxxxxxxxxxxxxxxx, DIRECT, f08c47fec0942fa0

要求：
- 不要自己编造 publisher ID
- 必须使用 AdSense 后台提供的真实代码段
- 用户没提供 publisher ID 时，先提醒用户提供，不要填占位值
- 不要把 ads.txt 内容写进 HTML 页面

## 3. 所有权验证

优先使用 AdSense 后台提供的 ads.txt 代码段验证方式，不要只依赖 meta 标签。
修改后需重新部署，部署完成先手动访问 /ads.txt 确认能打开，再回后台检查。

## 4. 排查清单

- ads.txt 文件名大小写错误
- 没有放在 public 目录
- 部署后根路径无法访问 /ads.txt
- 访问返回 403 / 401 / 重定向循环，或被 Cloudflare WAF、防盗链、bot 规则拦截
- publisher ID 写错
- 提交审核用了错误的网站或域名
- 修改后没有重新部署
- CDN 或缓存导致读取不到最新文件
- 存在多个 ads.txt 且内容不一致
- robots.txt、CDN 规则或中间件误拦了 Google 抓取

## 5. 修复流程

1. 判断项目框架
2. 检查是否存在 public/ads.txt
3. 检查文件名是否为小写
4. 检查内容是否为后台提供的真实代码段
5. 检查部署后 /ads.txt 是否可访问
6. 用正式域名检查 HTTP 状态码，确认不是 403/404/5xx、
   不重定向到其它域名、不返回 HTML 页面
7. 使用 Cloudflare 时，检查 WAF、缓存规则、重定向规则、
   Workers、中间件和安全等级是否影响 /ads.txt
8. 曾错误提交过网站的，建议在 AdSense 中删除后重新提交
9. 重新提交后等待抓取，确认状态变为已授权

## 6. 线上验证标准

访问 https://你的域名/ads.txt，确认：

- 返回 HTTP 200
- Content-Type 为 text/plain 或浏览器可直接显示的纯文本
- 正文只含 ads.txt 记录，不返回 HTML 模板
- 域名是提交 AdSense 审核的正式域名
- http:// 正确跳转到 https://，且最终 /ads.txt 仍返回 200
- www 和非 www 的选择与 AdSense 提交的规范域名一致

## 7. 输出要求

请输出：当前是否已有 ads.txt、当前路径、文件名大小写是否正确、
内容是否需要用户补充 publisher ID、部署后预计访问 URL 和状态码检查方式、
是否存在 Cloudflare/CDN/中间件/重定向拦截风险、需要修改哪些文件、
修改完成后用户需要做什么、部署后访问哪个 URL 验证、
是否建议删除网站后重新提交 AdSense。

同时检查广告位是否满足 PF-04（预留固定高度容器），
并说明本次改动对 CLS 的影响。
```

## 五、经验总结

遇到 `Ads.txt 状态未找到` 时，按出现频率排查：

1. Next.js 项目中 `ads.txt` 没放在 `public` 目录
2. 文件名大小写错误（必须是小写 `ads.txt`）
3. 所有权验证时没有选择 AdSense 提供的 `ads.txt` 代码段方式

修复后重新部署，浏览器访问 `https://你的域名/ads.txt` 确认可访问，
然后在 AdSense 中删除网站并重新提交。状态通常会从「未找到」变成「已授权」。

**接入广告后，务必重新跑一次性能实测**——`PF-01` 的三个指标都会受影响，
其中 CLS 变化最大。
