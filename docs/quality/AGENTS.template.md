# AGENTS.md

本项目使用一套可复用的 SEO 建站规范，目标是把已有网站模板改造成高质量、可上线、可扩展的 SEO 网站。

**规范版本：`2026-08-31`**（记录在 `project/SEO_LOG.md` 表头）

## 加载策略

不要一次读完所有文档。按任务类型加载：

### 常驻（任何任务都先读）

| 文件                         | 作用                        |
| -------------------------- | ------------------------- |
| `RULES.md`                 | 唯一规范来源。所有规则、分级、规则 ID 都在这里 |
| `project/PROJECT_BRIEF.md` | 本项目的定位、目标、技术栈与已做的项目级决策    |

### 按需加载

| 任务类型 | 追加读取 |
|---|---|
| 项目启动 / 首次规划 | `STRATEGY.md`、`project/PAGE_PLAN.md`、`project/SEO_PLAN.md` |
| 新增或改造页面 | `project/PAGE_PLAN.md`、`STYLE_GUIDE.md` |
| 写内容 / 补关键词文案 | `project/CONTENT_PLAN.md` |
| 视觉 / 组件 / 布局 | `STYLE_GUIDE.md` |
| 上线前后 / 质量审计 | `QUALITY_STANDARD.md`、`project/LAUNCH_CHECKLIST.md`、`project/SEO_PLAN.md` |
| 变现 / 广告 | `QUALITY_STANDARD.md`、`prompts/广告与变现.md` |
| 任何涉及 SEO 的收尾 | `project/SEO_LOG.md`、`project/创建输出表单.md` |

**为什么这样设计。** 旧版要求任何工作前读满 9 个文件（约 5 万字符），实际结果是跳读后声称读过。Agent 遵守 40 条规则的比例远高于 400 条。

`prompts/` 目录是给用户复制的启动提示词，**不是项目运行时的约束来源**，除非用户明确要求参考或修改。

## 开发前必须检查代码现状

写任何代码前，先确认：

- `package.json` 与框架版本
- 路由结构与页面目录
- 组件目录与样式系统
- 数据来源与内容组织方式
- 现有 metadata / sitemap / robots / canonical 的实现方式
- 构建命令与 lint 命令

判断后再决定：哪些页面保留、改造、删除或 noindex；哪些组件复用；哪些样式作为主风格；哪些 SEO 技术项需要补齐。

**技术栈以当前模板为准，不擅自更换框架或大规模重构。** 若模板无明确技术栈，默认 Next.js + TypeScript + Tailwind CSS + MDX/结构化内容数据，静态生成优先。

## 执行原则

- 以项目根目录的规范文件为准，不只依赖聊天上下文
- 不重写整个模板，除非用户明确要求
- 优先复用模板已有的页面结构、组件、样式系统与路由方式
- 不为了视觉效果牺牲 SEO、性能、可访问性和移动端体验
- 不为了 SEO 牺牲真实用户体验
- 不生成低质量薄页面、近重复页面、doorway pages 或只替换关键词的模板页

## 页面开发确认门

**新增页面、重做首屏、改变搜索意图、改变 URL、改变 index/noindex、改变核心模块顺序——必须先输出「页面格局布置方案」并等待用户确认，不得直接写代码。**

方案格式见 `project/PAGE_PLAN.md`。

**例外**（可跳过确认）：错别字修正、明显 bug 修复、已确认页面内的小范围样式修复、依照现有方案补充缺失的 metadata。

这道门是防止 Agent 一口气生成大批低质量页面的主要防线，不要因为「看起来只是个小页面」而绕过。

## 增量编辑要求

向已有页面补充内容或关键词文案时，规则见 `RULES.md` 的 KW-10 ~ KW-16。技术执行要求：

- 先定位页面路由、内容数据文件、组件文件、metadata 文件、sitemap / canonical 来源
- **不整文件重写，不复制新页面覆盖旧页面**
- TSX / JSX：在明确的 JSX 模块、数据数组项、FAQ 数组或 metadata 对象中局部补充
- Markdown / MDX / JSON / TS 数据：追加字段、追加段落或更新指定对象，不重排无关内容
- 保留原有 import、组件结构、样式类名、交互逻辑与数据字段
- 修改大量相似页面前，先做一个样例并验证，再批量应用
- 批量脚本只做结构化、可回滚的局部插入，不得用整文件字符串模板覆盖

修改后验证：能正常构建、原有内容仍在、无重复段落 / 乱码 / HTML 破损 / 组件嵌套错误、移动端布局未受影响。

## SEO 执行顺序

1. 信息架构 → 2. URL 规划 → 3. 页面类型定义 → 4. metadata 模板 → 5. sitemap / canonical / robots → 6. 核心页面 → 7. 批量页面模板 → 8. 博客模板 → 9. 内链系统 → 10. 批量生成

**禁止**：先批量生成薄页面；没有 sitemap 机制就生成海量页面；没有 canonical 策略就开放搜索页和筛选页；没有内链规划就创建深层页面；没有淘汰机制就无限扩页面。

## 自动检查

发布状态与证据边界先按 `QUALITY_STANDARD.md` 判断。任何 P0 未关闭时，不得用局部通过、总分或 AdSense `Ready` 覆盖发布阻断。

`RULES.md` 中标记 `⚙` 的规则由脚本验证，**不要靠人工承诺**：

```bash
node scripts/seo-check.mjs --base http://localhost:3000
```

标记 `🌐` 的规则在每次部署后验证：

```bash
node scripts/post-deploy-check.mjs --base https://你的域名
```

交付前必须跑过 `seo-check`，并在报告中附上结果。脚本报错未修复就交付，等同于未完成。

## 交付报告格式

每次完成开发、检查或修改后，最终输出必须包含：

1. **修改了哪些文件**
2. **完成了哪些页面或功能**（含 URL）
3. **`seo-check` 结果**：通过 / 失败项及处置
4. **规则符合性**：按规则 ID 说明。所有**必须**级规则的偏离都要单独列出并说明原因
   - 主关键词与其位置覆盖情况（KW-01）
   - 语义覆盖率与缺失项（KW-04）
   - canonical / index / sitemap 状态（IDX-01~06）
   - 核心页入链数（LINK-02）
5. **移动端与视觉检查结果**
6. **性能实测数值**（PF-01，涉及页面改动时）
7. **尚未完成的问题**
8. **需要用户决策的问题**
9. **type-check / lint / 测试 / 框架构建 / 平台等效构建结果**；OOM、挂起或跳过必须按失败报告
10. **是否已更新** `project/SEO_LOG.md` 与 `project/创建输出表单.md`；未更新须说明原因
11. **生产证据链**：commit、push、部署版本、生产 smoke、回滚条件与步骤
12. **广告站专项**（如适用）：AdSense 状态、`ads.txt`、广告页面边界、CMP 地区验证

### 不要做的事

- 不要报告「关键词密度已达 3%-5%」——该指标已废除，原因见 `RULES.md` 附录 E
- 不要在未跑 `seo-check` 的情况下声称检查通过
- 不要把**应该**级规则的偏离静默略过，要写进报告
